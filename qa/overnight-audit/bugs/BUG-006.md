# BUG-006 — Cron bearer compared with plain `!==`, not timing-safe; cron 500 leaks DB error text

- **Severity:** P3
- **File:** `apps/frontend/src/app/api/cron/cleanup/route.ts:22` (compare), `:29` (leak)

## Expected

A bearer secret comparison is constant-time, and error responses from a privileged endpoint do not expose database error text.

## Actual (code behaviour)

```ts
const secret = process.env.CRON_SECRET;
if (!secret || req.headers.get("authorization") !== `Bearer ${secret}`) return new Response("Unauthorized", { status: 401 });
```

The comparison is a plain string `!==` — not timing-safe (contrast `verifyWebhookSignature` in `lib/billing/cashfree.ts:154` and `safeEqual` in `lib/api/auth.ts:49-52`, which both use `timingSafeEqual`). Elsewhere in the same file, a list-users failure returns the Supabase error verbatim:

```ts
if (error) return Response.json({ ok: false, error: error.message }, { status: 500 });
```

and the `failures` list also embeds per-user error text (lines 48-58, 69).

## Evidence

- `apps/frontend/src/app/api/cron/cleanup/route.ts:22` — `!==` bearer comparison.
- `apps/frontend/src/app/api/cron/cleanup/route.ts:29` — `error.message` in the 500 JSON.
- `apps/frontend/src/lib/api/auth.ts:49-52` — the codebase already has a `safeEqual` helper for exactly this.

## Root cause

The cron route predates (or missed) the timing-safe comparison pattern used by the webhook and OAuth-state code, and its error path forwards driver errors like the API routes in BUG-005.

## Recommended fix

Use the existing `safeEqual` helper (or `timingSafeEqual` on hashed values) for the bearer check, and return a generic message on the 500 path while logging the detail server-side.

## Runtime repro: pending

Code review only; timing attacks over the network are low-signal (hence P3), and the 500 leak requires a DB failure behind a bearer-gated endpoint. No live repro attempted.
