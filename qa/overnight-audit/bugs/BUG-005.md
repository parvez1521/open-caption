# BUG-005 — Supabase/Postgres error text leaked to API clients in ~41 places

- **Severity:** P3
- **File:** `apps/frontend/src/lib/api/http.ts:15` (envelope echoes `details`)
- **Also:** ~41 `ApiFailure` call sites passing `error.message` as details/message

## Expected

API error responses carry a human-readable message and a code, never raw database/driver error text (table names, constraint names, Postgres hints, RLS policy names).

## Actual (code behaviour)

`failResponse` includes the `details` argument verbatim in the JSON body:

```ts
return NextResponse.json({ success: false, error: { code, message, ...(details !== undefined ? { details } : {}) } }, ...);
```

Call sites routinely pass a Supabase error message as that third argument (or inside the message), e.g.:

```ts
throw new ApiFailure("INTERNAL", "Could not load your brand profiles", full.error.message);
throw new ApiFailure("INTERNAL", "Could not start the payment: " + insertError.message); // checkout/route.ts
```

A grep over `apps/frontend/src/app/api` finds ~41 `ApiFailure` calls carrying `error.message` (brand, content, exports, growth, looks, device, guest/claim, checkout, videos). Any authenticated caller who triggers a DB failure receives the underlying Postgres/Supabase error text, which reveals schema internals useful for probing.

## Evidence

- `apps/frontend/src/lib/api/http.ts:15` — `details` spread into the error envelope.
- `apps/frontend/src/app/api/v1/billing/checkout/route.ts` — insert error message embedded in the response message.
- `apps/frontend/src/app/api/v1/brand/profiles/route.ts:60,69,80`, `apps/frontend/src/app/api/v1/content/route.ts:45`, `apps/frontend/src/app/api/v1/exports/route.ts:20` — `error.message` passed as details.
- Count: `grep -rn 'ApiFailure("[A-Z_]*", "[^"]*", .*error\.message' apps/frontend/src/app/api/ | wc -l` → 41.

## Root cause

No separation between the user-facing message and the diagnostic detail: handlers forward the driver error for debuggability and the envelope forwards it to the client.

## Recommended fix

Log `error.message` server-side and return a generic message/details to the client (or strip `details` from `failResponse` for `INTERNAL` codes). Keep validation details (zod flatten) — those describe the caller's own input, not the DB.

Code review only; needs live repro (trigger a DB error, e.g. call an endpoint with the billing table unapplied, and confirm the response body contains Postgres text). No secrets were observed in these messages in code review.
