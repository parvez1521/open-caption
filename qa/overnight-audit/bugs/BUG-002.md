# BUG-002 — Upload size/MIME limits enforced on client-declared values only; actual bytes never re-checked

- **Severity:** P2
- **File:** `apps/frontend/src/app/api/v1/projects/[id]/videos/route.ts:17-26`
- **Also:** `apps/frontend/src/app/api/v1/videos/[id]/complete/route.ts:22-24`, `apps/frontend/src/lib/api/storage.ts:31-36`

## Expected

The plan upload cap (Free 50 MB — `packages/shared/src/plans.ts:27`) and the video-type allowlist (MP4, MOV, WebM, MKV) are enforced against the bytes actually stored, so a caller cannot store a larger file or a non-video file by lying in the request.

## Actual (code behaviour)

The videos route compares the client-declared `body.size` and `body.mime` — both plain request fields — against the limits:

```ts
if (!(VIDEO_MIME_TYPES as readonly string[]).includes(body.mime)) {
  throw new ApiFailure("UNSUPPORTED_MEDIA", ...);
}
const cap = body.local ? limits.maxLocalBytes : limits.maxUploadBytes;
if (body.size > cap) {
  throw new ApiFailure("LIMIT_EXCEEDED", ...);
}
```

The route then hands back a signed upload URL (`signedPut`, `storage.ts:31-36`) with no size or content-type constraint on the upload itself. The complete step fetches the real stored size (`objectSize`) but only checks it is non-zero:

```ts
const size = local ? video.file_size : await objectSize(video.storage_path);
if (size === null || size === 0) throw new ApiFailure("CONFLICT", "The upload did not finish...");
```

It never compares the real size to the plan cap, and nothing anywhere sniffs the stored file's content type — the MIME check is a string comparison on a client-supplied field, and the storage extension is derived from that same field (`extFromMime`, `storage.ts:36-39`, falling back to the client-supplied filename extension).

## Evidence

- `apps/frontend/src/app/api/v1/projects/[id]/videos/route.ts:17,24` — checks use `body.mime` / `body.size`.
- `apps/frontend/src/app/api/v1/videos/[id]/complete/route.ts:22-23` — real size fetched but only null/zero-checked.
- `apps/frontend/src/lib/api/storage.ts:31-36` — `createSignedUploadUrl` with no size/content-type bound.

## Root cause

Trust boundary error: request-declared metadata is treated as fact, and the verification step that does see the real object (complete) does not re-apply the limits.

## Recommended fix

At complete time, compare the real `objectSize` against the caller's plan cap and reject (and delete) over-limit objects; verify the stored object's content type (e.g. storage metadata / magic bytes) against the allowlist before marking the video uploaded. Keep the client-side checks as UX only.
