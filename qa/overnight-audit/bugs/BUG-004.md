# BUG-004 — Device approve GET discloses any pairing code; POST lets any signed-in user claim it

- **Severity:** P3
- **File:** `apps/frontend/src/app/api/v1/device/approve/route.ts:9-16` (GET), `:19-31` (POST)

## Expected

A pairing code's details (device name, platform, status) are visible only to the user who will approve it, approval binds the device to the approving user only when that user is the one who owns the pairing, and pairing endpoints are rate-limited.

## Actual (code behaviour)

GET discards the authenticated user and reads any code through the admin client with no ownership check and no rate limit:

```ts
export const GET = route(async (req: Request) => {
  await requireUser(req);
  const code = normalize(new URL(req.url).searchParams.get("code") ?? "");
  if (!code) throw new ApiFailure("VALIDATION", "Missing code");
  const { data } = await getAdmin().from("device_codes").select("user_code, worker_name, platform, status, expires_at").eq("user_code", code).maybeSingle();
```

GET also does not call `requireCompanionsEnabled()` (POST does, line 19). POST then binds the device to whoever approves, keyed only by the code:

```ts
const { data, error } = await admin.from("device_codes")
  .update(body.approve ? { status: "approved", owner_id: user.id, ... } : { status: "denied", owner_id: user.id })
  .eq("user_code", code).eq("status", "pending")...
```

Any signed-in user who learns or guesses an 8-character code can view the pending device and approve it into their own account (or deny it, breaking the victim's pairing).

## Evidence

- `apps/frontend/src/app/api/v1/device/approve/route.ts:10` — `await requireUser(req);` with the result discarded.
- `apps/frontend/src/app/api/v1/device/approve/route.ts:13` — admin read by `user_code` only, no `owner_id` filter.
- `apps/frontend/src/app/api/v1/device/approve/route.ts:24-27` — approve/deny sets `owner_id: user.id` for any caller.
- No `rateLimit` call anywhere in this file (contrast `device/start/route.ts:18` and `device/token/route.ts:19,25`).

## Root cause

The pairing code is treated as the sole authenticator, but it is only 8 characters from a 32-symbol alphabet (`device/start/route.ts:11-16`) and the lookup endpoint is unauthenticated-by-ownership and unthrottled, so code secrecy is the only barrier and it is not reinforced.

## Recommended fix

Rate-limit approve GET/POST per user and per IP; require the companions flag on GET as well; and consider binding the code to the approving session more strongly (e.g. require the approver to have initiated the pairing, or add a short server-side approval nonce). At minimum, add the rate limit and the flag check.
